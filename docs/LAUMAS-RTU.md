# Laumas W100 / W200 over Modbus RTU

Status: adapter implemented and tested against a simulator. **Commissioning gate
H1 is not closed by this document or by the simulator.** See "What is verified
and what is not".

## Why a separate adapter

`scaleascii` expects a line stream such as `WT=28460;ST=1;...` and its parser is
a placeholder. The Laumas indicator on this site does not stream: it is a Modbus
RTU slave on RS485 that must be polled. `laumasrtu` is that poll client. It feeds
the same audited path as every other scale adapter:

```text
indicator bytes -> raw weight journal (hash chain, fsync) -> AuditedScaleReading -> workflow
```

## Wire protocol

One request, one fixed-size response, repeated every `-scale-poll` (default
100 ms).

```text
request   <slave> 03 00 06 00 05 <crc lo> <crc hi>      read holding registers 6..10
response  <slave> 03 0A <10 data bytes> <crc lo> <crc hi>   15 bytes
```

| Register | Bytes | Meaning |
|---|---|---|
| 6 | 0-1 | status word, **bit 11 = STABLE** |
| 7-8 | 2-5 | weight, signed 32-bit, most significant word first, kg |
| 9-10 | 6-9 | not decoded; preserved byte-for-byte in the audit record |

CRC is Modbus CRC-16 (poly `0xA001`, init `0xFFFF`), low byte first.
Serial settings proven on site: 9600 baud, 8 data bits, no parity, 1 stop bit,
slave address 1.

This register map comes from the Python prototype that ran against the real
indicator on `COM3`. It was not re-derived from the vendor manual.

## Decoding rules

* A reading is produced only from a frame that has the exact length, the right
  slave address, function `0x03`, byte count `0x0A` and a valid CRC.
* A Modbus exception frame (`0x83 ...`) is an error carrying the exception code.
* **Overload and indicator-fault bits are not decoded by default.** Their
  positions are not part of the verified map. They are opt-in masks
  (`-laumas-overload-mask`, `-laumas-fault-mask`); until they are confirmed
  against the manual and the display, the adapter will never claim `Overload` or
  `Fault` from a bit it has not been told about. A deck that is actually
  overloaded is therefore *not* detected by this adapter until the mask is set.
* The stable bit position can be overridden with `-laumas-stable-bit`.

## Failure behaviour

| Event | Result |
|---|---|
| Reply late (within `-scale-response-timeout`) | normal reading |
| Poll unanswered / truncated / CRC error | journaled (`TRANSPORT_ERROR` or `FRAME` with `parse_ok=false`), **no reading is emitted**, no value is carried over |
| `-scale-missed-polls` such polls in a row (default 3) | `OnFault` -> the workflow locks out an active transaction (same path as the ASCII scale) |
| Connection closed | fault immediately, then reconnect after `-scale-reconnect-delay` |
| Raw journal cannot be written | `Run` returns an error; no unaudited reading is ever delivered |

Isolated misses are tolerated on purpose: RS485 turn-around and USB adapters do
drop a poll now and then, and locking out a truck on one missed poll would be
wrong. What is *not* tolerated is inventing a value: a missed poll never turns
into a repeated "stable" weight.

Every poll is one raw-journal record. At 100 ms that is about 864,000 records a
day; plan journal retention and rotation (open gate H4) accordingly, or raise
`-scale-poll`. The stable confirmation count (`-stable-confirmations`) is in
frames, so changing the poll interval changes the confirmation time.

## Running it

Direct COM port (Windows):

```text
edge.exe -scale-protocol laumas-rtu -scale-serial COM3 -scale-baud 9600 -scale-slave 1
```

Through a transparent serial-to-Ethernet gateway (raw/TCP server mode, **not**
Modbus TCP mode, because the frames are RTU frames):

```text
edge.exe -scale-protocol laumas-rtu -scale-addr 192.168.10.20:4001 -scale-slave 1
```

The native COM implementation uses only `syscall` (no CGO, no new module). It
mirrors the settings pyserial applies on Windows (binary mode, DTR and RTS
asserted, no flow control) because that is what ran against the real indicator.
**It has never been run against a real COM port**; only open-failure handling is
tested.

## What is verified and what is not

Verified in CI:

* CRC against the published Modbus example (`01 03 00 00 00 01 -> 84 0A`).
* Seven golden response frames decode to the expected weight/stable flag, and
  re-encode byte for byte.
* Every malformed-frame class is rejected (short, bad CRC, wrong slave, wrong
  function, bad byte count, trailing byte, exception frame); a fuzz target found
  no frame that is accepted but does not round-trip.
* The collector against a simulated indicator: exact bytes journaled, dropped and
  corrupt polls, silent indicator and recovery, journal failure, wrong slave.

Not verified (needed to close H1):

* **The golden frames were generated by the Python prototype's code, not captured
  from the device.** Capture real frames at several weights and compare each with
  the physical display.
* The status bits for overload and fault.
* Behaviour on a real COM port or a real gateway, including turn-around timing.
* Whether 100 ms polling is acceptable to the indicator and the journal volume.
